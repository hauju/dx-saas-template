## Prerequisites

Make sure you have the following installed:

- **Rust** (latest stable) — [rustup.rs](https://rustup.rs)
- **Dioxus CLI** — `curl -sSL http://dioxus.dev/install.sh | sh`
- **Bun** — [bun.sh](https://bun.sh) (for Tailwind CSS)
- **Docker** — for PostgreSQL and Mailpit

## Quick Start

<Steps>
  <Step title="Clone the repository">
    ```bash
    git clone https://github.com/your-org/dx-saas-template.git
    cd dx-saas-template
    ```
  </Step>
  <Step title="Bootstrap your env file">
    ```bash
    just bootstrap
    ```

    This copies `.env.example` to `.env` and generates a fresh `SESSION_SECRET` for you.

    The defaults sign you in by email code (Mailpit catches the mail) with no identity provider to set up. Edit `.env` if you need to change:
    - `DATABASE_URL` — PostgreSQL connection string (default: `postgres://dx_saas:dx_saas@localhost:5432/dx_saas`)
    - `BASE_URL` — Your app's base URL (default: `http://localhost:8080`)
    - `COMING_SOON` — on by default; set `false` to see the landing page instead of the pre-launch page
  </Step>
  <Step title="Start infrastructure">
    ```bash
    docker compose up -d
    ```

    This starts:
    - **PostgreSQL 18** on port `5432`
    - **Mailpit** with SMTP on `1025` and web UI on `8025`, where the sign-in codes arrive

    Schema migrations in `migrations/` are embedded in the binary and applied automatically on first boot.

    FerrisKey is optional. `just ferriskey` starts one on port `8090` and creates the realm and client the app expects; see [Authentication](/docs/guides/authentication#ferriskey-mode).
  </Step>
  <Step title="Install frontend dependencies">
    ```bash
    bun install
    ```
  </Step>
  <Step title="Run the development server">
    ```bash
    dx serve --addr 0.0.0.0
    ```

    The app will be available at `http://localhost:8080`. The dev server auto-reloads on code changes and runs Tailwind CSS automatically.
  </Step>
</Steps>

## Project Commands

`just ferriskey` is the one optional extra: it starts FerrisKey from the `ferriskey` compose profile and runs `scripts/ferriskey-bootstrap.sh` against it.


| Command | Description |
| --- | --- |
| `dx serve --addr 0.0.0.0` | Start development server with hot reload |
| `dx build --release --platform web` | Production build |
| `bunx @tailwindcss/cli -i tailwind.css -o ./assets/tailwind.css` | Build Tailwind CSS manually |
| `cargo fmt --all -- --check` | Check formatting |
| `cargo clippy --workspace --all-targets -- -D warnings` | Lint |
| `cargo machete` | Detect unused dependencies |

<Note>
The `dx serve` command automatically compiles Tailwind CSS. You only need to run the Tailwind CLI manually for CI builds or when `dx serve` is not running.
</Note>

## Environment Variables

<AccordionGroup>
  <Accordion title="Core Settings">
    - `DATABASE_URL` — PostgreSQL connection string
    - `BASE_URL` — Public URL of your application
    - `SESSION_SECRET` — Hex-encoded session signing key (64+ bytes)
    - `SECURE_COOKIES` — Set to `true` in production (HTTPS)
    - `COMING_SOON` — `true` replaces the landing page with a coming-soon page and waitlist (see the Waitlist accordion)
  </Accordion>
  <Accordion title="Registration & Waitlist">
    - `OPEN_REGISTRATION` — `true` lets any address sign up; see [Authentication](/docs/guides/authentication) for the allowlist alternative
    - `CAPTCHA_URL` / `CAPTCHA_SITE_KEY` / `CAPTCHA_SECRET_KEY` — Bollwark captcha in front of registration and the waitlist form
    - `COMING_SOON` — while `true`, `/` is a coming-soon page whose form writes to the `waitlist` table (`SELECT count(*) FROM waitlist` to see how many are waiting); login, docs and the dashboard stay reachable
  </Accordion>
  <Accordion title="Authentication">
    - `AUTH_MODE` — `local` (default: email OTP + passkeys, nothing else to run) or `ferriskey`
    - `TOS_VERSION` — terms version users must accept on login; unset disables the step
    - `TRUST_PROXY_HEADERS` — Set to `true` when behind a reverse proxy
    - FerrisKey mode only: `FERRISKEY_URL` (local instance: `http://localhost:8090/api`), `FERRISKEY_ISSUER_URL` _(optional)_, `FERRISKEY_REALM`, `FERRISKEY_CLIENT_ID`, `FERRISKEY_CLIENT_SECRET` — `just ferriskey` produces all of these
  </Accordion>
  <Accordion title="Email (SMTP)">
    - `SMTP_HOST` — SMTP server host
    - `SMTP_PORT` — SMTP port (default: `1025` for Mailpit)
    - `SMTP_USER` — SMTP username (optional for Mailpit)
    - `SMTP_PASSWORD` — SMTP password (optional for Mailpit)
    - `SMTP_FROM` — Sender email address
  </Accordion>
  <Accordion title="Billing (Polar)">
    - `POLAR_ACCESS_TOKEN` — Polar API access token
    - `POLAR_WEBHOOK_SECRET` — Webhook verification secret
  </Accordion>
  <Accordion title="Sentry (optional)">
    Requires building with `--features sentry`.

    - `SENTRY_DSN` — Sentry project DSN
    - `ENVIRONMENT` — environment tag (e.g., `development`, `production`)
  </Accordion>
</AccordionGroup>

## Changing the database schema

Queries use `sqlx`'s compile-time-checked macros, so column names and types are
verified against the schema when you build. The metadata lives in `.sqlx/` and is
committed, which is what lets a fresh clone build with no database running.

<Warning>
After editing any SQL or adding a migration, regenerate the metadata:

```bash
docker compose up -d
cargo sqlx prepare -- --no-default-features --features server
```

Editing a query without re-preparing fails the next build. Editing a **migration**
without re-preparing does not — cached entries are keyed by the query text, so
untouched queries keep matching now-stale metadata and compile fine, failing only
at runtime. CI guards this by building against a real database.
</Warning>

## Renaming the project

After cloning, give the project its own name:

```bash
just rename my-new-project
```

This rewrites the package name, Postgres database/user name, tracing filter, Dockerfile binary path, and docs in one shot. Run `cargo build` afterwards to regenerate `Cargo.lock`.
